# آماده‌سازی حساب‌ها و محیط Firebase

این راهنما برای مدیر مجاز پروژه است. در محیط فعلی هیچ حساب Google به Firebase CLI متصل نیست و پروژه، کاربران، صورتحساب یا تنظیمات واقعی توسط عامل ساخته نشده‌اند. هرگز رمز حساب، توکن، فایل کلید حساب سرویس یا کد دومرحله‌ای را در گفتگو یا مخزن وارد نکنید.

## ساخت محیط آزمایشی

۱. مالک مجموعه در Firebase Console یک پروژه **آزمایشی جدا** ایجاد کند، Authentication و ورود Email/Password و Cloud Firestore را فعال کند و برنامه Android با package `com.alnasser.smartfleet` ثبت کند. Cloud Functions ممکن است نیاز به Blaze، صورتحساب، محدودیت بودجه و تأیید مالک داشته باشد. اطلاعات عمومی Project ID، App ID و Web API Key برنامه برای صفحه اتصال کافی است؛ اینها مجوز مدیریتی نیستند.
۲. مدیر مجاز در Authentication یک حساب ایمیل/رمز برای مدیر بسازد و UID آن را دریافت کند. رمز را در CLI، مخزن یا گفتگو قرار ندهید. برای مراحل بعد کاربران راننده هم باید حساب Auth و سند پروفایل `active: true, role: "driver"` داشته باشند. ابزار ثبت و دعوت کاربر از داخل برنامه هنوز وجود ندارد.
۳. در محیط مدیر، با هویت Google دارای مجوز لازم برای Firebase Admin و Firestore به صورت ایمن Application Default Credentials را تنظیم کنید. وابستگی‌ها را با `npm ci --prefix firebase/functions` نصب کنید. فقط برای یک مجموعه کاملاً جدید دستور زیر را با مقادیر واقعی اجرا کنید:

```sh
node firebase/functions/scripts/bootstrap-tenant.cjs --project=PROJECT_ID --tenant=TENANT_ID --manager-uid=EXISTING_AUTH_UID --confirm-new-tenant
```

اسکریپت وجود حساب Auth و فعال‌بودن آن را بررسی و در تراکنش یک مجموعه فعال، پروفایل مدیر، مقادیر اولیه سوخت و audit اولیه می‌سازد. اگر مجموعه وجود داشته باشد متوقف می‌شود و هرگز نقش یک مجموعه موجود را تغییر نمی‌دهد. Project ID باید متعلق به پروژه انتخابی باشد؛ هویت اجراکننده مسئول انتخاب آن است. ایجاد حساب Auth، تعیین صورتحساب، نصب ابزار Google و deploy خودکار انجام نمی‌شود. از فایل کلید خصوصی در مخزن استفاده نکنید.
۴. Rules، indexها و Functions مخزن پس از بررسی مدیر روی همان پروژه آزمایشی deploy شوند. ورود، نقش، آفلاین، تداخل و دسترسی‌های غیرمجاز باید روی چند گوشی آزمون شوند. پروژه واقعی نباید بدون ارزیابی امنیت و فرایند انتشار جدا به کار گرفته شود.

## انتساب راننده

مدیر در مسیر اتصال واقعی برنامه می‌تواند خودروی موجود را انتخاب و UID راننده فعال را وارد کند. Functions نقش مدیر و وضعیت مجموعه، راننده و خودرو را داخل تراکنش بررسی می‌کنند؛ ثبت و خاتمه انتساب با audit و شناسه پایدار انجام می‌شود. هم‌زمانی ساخت دو انتساب جدید برای یک زوج راننده/خودرو با lock اتمیک کنترل می‌شود. انتساب‌های قدیمی که مستقیماً در کنسول ساخته شده‌اند lock ندارند و باید پیش از استفاده از این قابلیت توسط مدیر بررسی و از طریق فرآیند مهاجرت امن سامان‌دهی شوند؛ ادعای پیشگیری از تکرار آنها وجود ندارد. انتساب خاتمه‌یافته حذف نمی‌شود. درخواست‌های آفلاین راننده که پس از خاتمه انتساب برسند ممکن است رد شوند و نیازمند بررسی دستی‌اند.

ایجاد و غیرفعال‌سازی کاربران، نقش حسابدار، سیاست دستگاه مجاز، و ویرایش نرخ‌ها در برنامه کامل نشده‌اند. اتصال به پروژه و استقرار و تست چنددستگاهی واقعی هنوز انجام نشده است.

در [اجرای CI 42234946990](https://github.com/Companymeelano/Ranande/actions/runs/42234946990)، تست تراکنش انتساب، هم‌زمانی، مجوز، callable و bootstrap روی Firebase Emulator موفق شد. این امر به معنی ساخت حساب در Firebase واقعی یا deploy نیست.

### آماده‌سازی ایندکس پلاک برای ناوگان موجود
ثبت خودرو اکنون فقط از تابع مدیر انجام می‌شود و تا آماده‌سازی ایندکس پلاک بسته است؛ مستأجر تازه‌ای که با bootstrap فعلی ساخته شود از ابتدا آماده است. برای مستأجر قدیمی ابتدا نسخه پشتیبان بگیرید و در پنجره نگهداری **همه نویسندگان ممتاز/Admin و نسخه‌های قدیمی** را متوقف کنید؛ قوانین جدید و توابع را هماهنگ با نسخه جدید برنامه منتشر کنید. با اعتبار ADC مجاز و شناسه واقعی، روی محیط درست اجرا کنید:

```sh
node firebase/functions/scripts/migrate-vehicle-plates.cjs --project=PROJECT_ID --tenant=TENANT_ID --confirm-maintenance
```

اسکریپت حداکثر ۲۰۰ خودرو را در یک تراکنش بررسی و ایندکس و گزارش ممیزی را ایجاد می‌کند. پلاک نامعتبر، تکرار پس از نرمال‌سازی، قفل متناقض یا تعداد بیشتر باعث توقف بدون تغییر می‌شود؛ ابتدا با بررسی انسانی مشکل را حل کنید. قبل از آغاز مجدد کار، نتیجه و داده‌ها را بررسی کنید. این ابزار مانع تغییرات مستقیم توسط Admin SDK نیست؛ تمام مسیرهای ممتاز باید این ایندکس را رعایت کنند. عدم رعایت پنجره نگهداری یا دستکاری مستقیم داده تضمین یکتایی را از بین می‌برد. برای ناوگان بزرگ‌تر مهاجرت کنترل‌شده اختصاصی لازم است؛ پرچم آمادگی را دستی فعال نکنید.

ثبت مشتری واقعی فقط توسط مدیر فعال و از `createCustomer` انجام می‌شود و باید تابع و قوانین جدید با هم منتشر شوند. اطلاعات مشتری حساس است؛ امکان مشاهده فقط برای مدیر تعریف شده و از درج اطلاعات غیرضروری خودداری کنید. نمایش برنامه تا دریافت فهرست از سرور پنهان است، اما این به معنی پاک‌شدن خودکار cache داخلی Firestore یا تضمین لغو فوری دسترسی آفلاین نیست؛ سیاست نگهداری داده و آزمون امنیت دستگاه پیش از بهره‌برداری لازم است. ثبت آفلاین و امکان ویرایش فعلاً موجود نیست. در نتیجه نامشخص، بدون تغییر فرم دوباره تلاش کنید؛ شناسه درخواست پس از پایان فرایند پایدار نیست، پس ابتدا فهرست را بررسی کنید. نام و شماره یکتا فرض نمی‌شوند؛ ایجاد رکورد تکراری با شناسه جدید ممکن است.
